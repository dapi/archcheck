# Каталог архитектурных правил

Проверено по первичным источникам 2026-10-05. Примеры ниже — варианты контрактов,
а не универсальные требования к любому проекту. «Можно сейчас» означает, что
контракт выражается текущими запрещающими правилами archcheck для наблюдаемых
прямых связей; это не обещает полноту разрешения вызовов индексатором.

| Семейство | Пример договора | Возможности archcheck сейчас | Источник |
|---|---|---|---|
| Запрещённая зависимость | UI не импортирует реализацию хранилища | Можно: `from`, `to`, `edges: [imports, calls]` | [Import Linter: forbidden](https://import-linter.readthedocs.io/en/stable/contract_types/forbidden/) |
| Слои | Controller обращается к Persistence через Service; обратные зависимости запрещены | Прямые запрещённые пары можно перечислить. Слои и проверка полноты их классификации не встроены | [ArchUnit: layers](https://www.archunit.org/userguide/html/000_Index.html#_layer_checks), [Import Linter: layers](https://import-linter.readthedocs.io/en/stable/contract_types/layers/) |
| Домен и адаптеры | Domain не зависит от Application или конкретного Adapter | Можно перечислить прямые запреты; выбор такой архитектуры должен быть решением проекта | [ArchUnit: onion architecture](https://www.archunit.org/userguide/html/000_Index.html#_onion_architecture) |
| Независимые модули | Orders и Billing не зависят друг от друга | Прямые зависимости можно запретить в обе стороны. Полная независимость, включая косвенные пути, пока не поддерживается | [Import Linter: independence](https://import-linter.readthedocs.io/en/stable/contract_types/independence/) |
| Защищённый модуль и публичный API | Реализация платёжного клиента доступна только его фасаду | Можно запретить обращения из явно перечисленных каталогов. Автоматический allow-list, дополнение множества селекторов и модель public API отсутствуют | [Import Linter: protected](https://import-linter.readthedocs.io/en/stable/contract_types/protected/), [ArchUnit: modularization](https://www.archunit.org/userguide/html/000_Index.html#_modularization_rules) |
| Отсутствие циклов | A → B → C → A запрещено | Не реализовано; нужен поиск циклов выбранного графа и группировка модулей | [dependency-cruiser: circular](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md#circular) |
| Транзитивный запрет | UI не должен достигать Storage даже через промежуточный модуль | Не реализовано; прямая запрещённая связь и достижимость имеют разный смысл | [dependency-cruiser: reachable](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md#reachable---detecting-dead-wood-and-transient-dependencies) |
| Обязательная зависимость | Каждый Controller должен наследовать BaseController | Не реализовано. Запрет `extends` поддержан, требование наличия `extends` — нет | [dependency-cruiser: required](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md#required) |
| Размещение, имена и аннотации | Класс с определённой ролью лежит в нужном пакете и имеет нужную аннотацию | Не реализовано. Селектор имени выбирает узлы, но не утверждает свойство каждого узла | [ArchUnit: what to check](https://www.archunit.org/userguide/html/000_Index.html#_what_to_check) |

CodeGraph / GoCPG отдельно описывает условия доверия результату: классификацию
исходников, capabilities анализатора, resolution coverage, свежесть графа,
baseline и исключения. Это другой проект, не используемый нами индексатор
colbymchenry/codegraph. [Руководство архитектурного контроля GoCPG](https://codegraph.ru/docs/ru/guides/ARCHITECTURE_CONTROL_ADOPTION.html).

## Чем исходный BYOA отличается от ArchUnit и archcheck

Публичный [BYOA-интерфейс Repo Health](https://medrenta.ru/) описывает процесс:
агент изучает репозиторий через stats, предлагает правила под конкретные риски,
проверяет их на намеренно нарушающем fixture через validate_rule, калибрует
по находкам search и передаёт YAML детерминированному сканеру.
ИИ участвует в подготовке правил; результаты сканирования определяет движок.

Это более широкий процесс статического анализа: публичный промпт перечисляет
patterns, constraints, синтаксические отношения, а для полного scan — секции
dataflow, call_context, types, domain и metrics. По описанию сайта search
исполняет только одиночный pattern с constraints. Architecture DSL с компонентами
и контрактами назван отдельной схемой, которую онлайн-инструменты BYOA
не поддерживают. Поэтому BYOA pattern rules и архитектурные контракты GoCPG
нельзя считать одним интерфейсом. Это сведения из публичного клиентского
промпта; фактическая реализация серверного полного scan нами не проверена.

[ArchUnit](https://www.archunit.org/userguide/html/000_Index.html) — библиотека
архитектурных тестов на Java: правила задаются программным DSL, проверка
использует Java bytecode и запускается в тестовом процессе, включая JUnit.
Подготовку таких тестов тоже можно поручить агенту. Поэтому наличие ИИ
само по себе не создаёт нового вида архитектурного анализа; существенны
модель кода, выразительность правил и проверенные возможности движка.

Текущий archcheck реализует узкую проверку запрещённых прямых структурных
связей по SQLite-индексу colbymchenry/codegraph. В нём нет pattern DSL,
калибровочного API, dataflow/taint, сложных архитектурных контрактов,
персональных профилей сайта или рейтинга. Он не воспроизводит весь исходный
BYOA-сервис. Для его расширения сначала нужны воспроизводимые правила и
fixture-кейсы, а затем выбор подходящего движка под требуемые факты.

## Как проверять правило

Для каждого правила нужен маленький исходный проект с заранее заданными
ожидаемыми результатами, проиндексированный настоящим CodeGraph:

1. Разрешённая связь даёт `no_observed_violations`, exit 0.
2. Намеренное нарушение даёт `violations`, exit 1, нужный rule ID, endpoints и строку.
3. Исправление исходника и синхронизация снова дают exit 0.
4. Допустимое объявление или type-level связь не принимаются за запрещённый вызов.
5. Пустой селектор, несовместимый или устаревший индекс блокируют проверку, exit 2.

Для будущих циклов нужны пары «цикл / разорванный цикл». Для транзитивности —
«запрещённая цепочка / разрешённая цепочка». Для обязательного наследования —
«нужная база / отсутствующая или другая база». Это план кейсов, пока не готовые тесты.

## Какие тесты уже есть

- [Go-тесты адаптера](../internal/check/check_test.go) проверяют findings и строки,
  дедупликацию, read-only чтение, чистый граф, версии, целостность, JSON metadata,
  свежесть файлов, пустые селекторы, ошибки парсинга, строгий режим, безопасные
  пути, YAML, селекторы и исключение interface dispatch bridges.
- [Go-тесты CLI](../cmd/archcheck/main_test.go) проверяют, что init не перезаписывает
  правила, ошибки возвращаются в JSON и неправильные команды дают ненулевой код.
- [Интеграционные кейсы](../integration/run.py) строят реальные индексы JS и Ruby,
  находят нарушения, исправляют исходники, проверяют синхронизацию новых файлов
  и блокировку устаревшего индекса. TypeScript-кейс отдельно различает
  синтетический вызов interface → implementation и реальную связь implements.
- [Локальный verifier](../scripts/verify-project.py) сверяет выбранные файлы с
  индексом и результат контрольного запрета с независимым SQL-запросом.
  SQL-проверка подтверждает адаптер и evaluator, но не корректность самого resolver.

Покрытие не равно полному доказательству: интеграционные кейсы не охватывают
все шесть типов связей, способы импорта, Ruby-метапрограммирование и особенности
каждого фреймворка. Реальные проекты нужны для поиска пропусков и ложных
срабатываний; один запуск без findings не заменяет специально нарушающий кейс.
